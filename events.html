Special Topic: Attached Intermediate Events

Attached intermediate events are commonly used as cancel conditions or boundary events on tasks (e.g., an attached timer triggers an alternative 'Escalation' path if a task isn't completed in time).

Easy: Message Start

Model a process that starts *only* when a 'Supplier Confirmation Received' message arrives. This trigger should immediately start the 'Validate Supplier Confirmation Data' task.

Elements Needed:

❌ Mistake 1: Wrong Naming (Active vs. Passive)

Events are triggers or results, so they must have passive names (e.g., "Order Received"). Tasks are actions, so they get active names (e.g., "Receive Order"). This is the most common mistake.

🔴 BAD

Using "Process the order" (an action) for a Start Event is incorrect.

🟢 GOOD

"Supplier Confirmation Received" is a perfect passive name for a Start Event for The *task* is "Validate Supplier Confirmation".

❌ Mistake 2: Wrong Trigger Type

Don't use a Timer event if the process is *reacting* to an external action. A Timer (clock icon) *forces* the process to start at a set time. A Message (envelope icon) *waits* for an external trigger to arrive.

🔴 BAD

This is wrong if you are *waiting* for a confirmation. This model will *force* a sync at 2:00 AM, even if no confirmation was sent.

🟢 GOOD

This is correct. The process will only start *when* the "Supplier Confirmation" actually arrives, whether it's at 2:00 AM or 3:15 PM.

❌ Mistake 3: Confusing Timer Logic (Start vs. Delay vs. Deadline)

All timers are not the same. Using the wrong one breaks the logic.

  • Start Timer (single border): Only goes at the *beginning*. Triggers the process *at* a specific time (e.g., "Every Monday 9 AM").
  • Intermediate Timer (double border): Goes *during* the process. Creates a *delay* (e.g., "Wait for 24 Hours").
  • Attached Timer (on task boundary): A "deadline" that triggers an escape path if the task isn't done in time.

🟢 GOOD

You use an Intermediate Timer (double border) to delay a process. It has 1 incoming flow and 1 outgoing flow, so the process waits for it.

🟢 GOOD

This model correctly uses a Start Timer ("Every Monday at 02:00") and an Attached Timer ("Wait 24 Hours") as a deadline on the task.

❌ Mistake 4: Using Sequence Flow Between Pools

You cannot use a solid-line Sequence Flow to connect two different Pools (e.g., "Customer" and "Supplier"). Sequence Flows only work *inside* a single Pool. To communicate between pools, you must use a dashed-line Message Flow.

🟢 GOOD

This is correct. A dashed Message Flow connects a *Throwing* event (dark icon) in one pool to a *Catching* event (light icon) in the other.

❌ Mistake 5: Process "Dead Ends"

Every single path in your process must finish at an End Event (thick single border). A common mistake is leaving a gateway path (like a "No" branch) hanging. This creates a "dead end," and the process will get stuck.

🔴 BAD

Every Branch here doesnt have a End Event and so the Process is Incompleted

🟢 GOOD

This is correct. And it make sures the process is finished.

❌ Mistake 6: Multiple Unrelated Processes in One Diagram

A single BPMN diagram should represent *one* end-to-end process. It should have a clear beginning and end. Modeling two completely separate processes (e.g., "Hiring" and "Invoicing") in the same file just because they are in the same department is a critical error. This makes the diagram unreadable and un-executable.

🔴 BAD

In This diagram, 3 Process are mentioned and creates confuses what is this BPMN about?

🟢 GOOD

This is a perfect, simple process. It makes sures one process is properly defined

❌ Mistake 7: Clutter & Overusing Intermediate Events

Events should mark *significant* milestones, delays, or triggers. A common mistake is to add a plain Intermediate Event (double circle) after *every single task* to say "Task Done". This adds zero value and creates massive visual clutter. Let the Sequence Flow arrow show that the task is done.

🔴 BAD

Sequence Flow already means Task is Completed so its not neccessary to show it as intermediate event.

🟢 GOOD

This flow is clean. There is no "Draft Done" event or "Review Done" event. The arrow itself implies the process moves to the next step.
